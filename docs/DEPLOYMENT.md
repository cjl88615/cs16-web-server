# 虚拟机、网络与验收

## 建议配置（规划值，不是实测容量承诺）

| 场景 | CPU | 内存 | SSD |
| --- | --- | --- | --- |
| 小规模试运行，约 4–8 个总角色 | 2 vCPU | 4 GB | 40 GB |
| 推荐起点，目标 8–16 个总角色 | 4 vCPU | 8 GB | 60 GB |
| 目标超过 16 人或大量高难度 BOT | 先测单核负载，再决定 4–6 vCPU | 8–12 GB | 60–80 GB |

总角色包括真人和 BOT。以上是留有系统、Docker 构建、缓存和日志余量的工程预算。不能把 vCPU 数直接换算为玩家数；宿主机争抢和单核性能会影响游戏帧时间。增加空闲核数不一定改善单个游戏进程的瓶颈。

虚拟机：x86_64 Linux，建议 Debian 12/13 或 Ubuntu 24.04，安装最小系统、SSH、Docker Engine 与 Compose 插件即可。不需要桌面环境或 GPU 直通；游戏图形由玩家浏览器渲染。推荐固定内存，避免游戏时持续换页；日志已限制为 10 MB × 3。构建阶段的磁盘/内存需求高于仅运行阶段。

## 局域网

桥接到同事可直接访问的 VLAN，使用固定 IP 或 DHCP 保留。`.env` 中的 LAN_IP 必须等于玩家能访问的 VM 地址。页面和 UDP 不能一通一不通。

默认开放范围仅限获准的内部网段：
- TCP 27016：网页、资源、WebSocket 信令。
- UDP 27018：WebRTC 对局流量。

Compose 将端口绑定到 LAN_IP。跨 VLAN 时检查路由与访问控制；NAT/访客 Wi-Fi 客户端隔离可能阻断 UDP。页面打开成功不能证明游戏连接成功。不要为方便而把整个 VM 防火墙关闭，也不要把公网反代当作 UDP 联机替代品。

## 修改与恢复

先保存 `.env`，再记录当前 `git rev-parse HEAD` 与镜像 ID。更新代码和构建完成后再替换容器。这个版本尚未设计持久化玩家账号、战绩数据库或网页管理权限，不要假设存在这些能力。

`.env` 改动用 `docker compose up -d --force-recreate`，仅 `restart` 不会重新读取 Compose 的环境变量配置。BSP、插件或源码改动需要重新构建。BOT 导航与学习数据目前在容器文件层，重新创建容器会恢复镜像内默认数据；不要把学习数据视为持久存档。

## 需要真实验证的内容

正式开放前至少在两台同事电脑上验证：一人进队后出现 BOT；第二人加入后 BOT 数量减少；一人退出后按目标补回；切换地图后 BOT 导航正常；战斗、声音、购买、中文快捷菜单正常；连续 30 分钟无断开或明显卡顿。

逐档测试 8、12、16 总角色，同时记录 `docker stats`、CPU 每核占用、实际内存和客户端延迟。CPU 单核长期接近满载、延迟波动或出现丢包时，先减少 BOT 数量/难度，再调整 CPU 资源。不要只凭服务器总体 CPU 百分比判断是否有余量。

## 自定义地图

`fy_iceworld` 不随此版本保证提供。加入自定义地图时要同时具备：合法取得的 BSP 和附属资源、匹配的 YaPB `.graph`、包含新资源的网页 ZIP 与新的版本清单。仅把 BSP 放进服务器目录会造成客户端缺资源，只有地图没有导航也不代表 BOT 能正常游玩。
