# 虚拟机、网络与验收

## 建议配置（规划值，不是实测容量承诺）

| 场景 | CPU | 内存 | SSD |
| --- | --- | --- | --- |
| **默认：1–4 真人与 BOT 补位，总目标 5 人** | **2 vCPU** | **2 GB** | **40 GB（含编译缓存）** |
| 性能确认后扩展到 6–8 总席位 | 2 vCPU | 2 GB | 40 GB |
| 更复杂地图/人数 | 先以单核使用率和帧时实测决定 | 仍以 2 GB 为评估约束 | 40 GB |

总角色包括真人和 BOT。以上是留有系统、Docker 构建、缓存和日志余量的工程预算。不能把 vCPU 数直接换算为玩家数；宿主机争抢和单核性能会影响游戏帧时间。增加空闲核数不一定改善单个游戏进程的瓶颈。

虚拟机：x86_64 Linux，建议 Debian 12/13 或 Ubuntu 24.04，安装最小系统、SSH、Docker Engine 与 Compose 插件即可。不需要桌面环境或 GPU 直通；游戏图形由玩家浏览器渲染。推荐固定内存，避免游戏时持续换页；日志已限制为 10 MB × 3。构建阶段的磁盘/内存需求高于仅运行阶段。

## 2 核 2GB 低配构建与运行

**只安装** Debian 最小系统、SSH、Docker Engine、Docker Buildx 和 Compose。无需桌面环境、浏览器、独立 GPU 或数据库；玩家在自己的电脑上渲染游戏和解压网页资源。

本项目的**构建**（SteamCMD 下载、32 位 C/Go 编译、npm 打包）可能比运行耗费更多内存。默认使用：

~~~bash
cp .env.example .env
# 把 LAN_IP 改为专用 VM 的真实内网地址
docker compose config --quiet
sh scripts/build-2gb.sh
docker compose up -d --no-build
docker compose ps
~~~

构建脚本使用独立 BuildKit builder，设定并行度为 1，镜像只在本地加载，不对外公开发布游戏资产。构建阶段如出现 OOM，可在磁盘空间允许且原本没有 Swap 的情况下临时创建约 2 GB Swap，构建完成后停用；**正式运行容器不允许换页来假装有更多内存**。避免在此 VM 上同时构建其他镜像或运行其他服务。

低配默认值：`MAX_PLAYERS=8`，`BOT_QUOTA=5`（真人 + BOT 总目标），`BOT_DIFFICULTY=2`，进程受 1536 MiB 内存上限保护，给 Debian/Docker 留约 512 MiB。未设置 Docker CPU 硬配额，避免突发战斗时被 CFS 节流。Go 软内存预算 `GOMEMLIMIT=384MiB` **不**包含 C/Xash 引擎全部分配，必须看 Docker 总内存，而非只看 Go 堆。

按以下顺序扩容验证：3 → 5 → 6 → 8（均为真人＋BOT 合计）。每档至少对战 30 分钟、跑多张地图；重点看单核 CPU、容器 RSS、OOMKills、玩家丢包与延迟波动。查看 `docker stats cs16-web-server`、`free -h`、`vmstat 1`。若出现帧时间变差，先把 `BOT_QUOTA` 降到 3 或 4，再排查单核 CPU/地图导航/UDP，而不是盲目增加内存或牺牲联机安全性。

**未做真实 2 vCPU / 2GB 的持续对局压测前，不能承诺 8 名真人及大量 BOT 同时流畅运行。**

## 局域网

桥接到同事可直接访问的 VLAN，使用固定 IP 或 DHCP 保留。`.env` 中的 LAN_IP 必须等于玩家能访问的 VM 地址。页面和 UDP 不能一通一不通。

默认开放范围仅限获准的内部网段：
- TCP 27016：网页、资源、WebSocket 信令。
- UDP 27018：WebRTC 对局流量。

Compose 将端口绑定到 LAN_IP。跨 VLAN 时检查路由与访问控制；NAT/访客 Wi-Fi 客户端隔离可能阻断 UDP。页面打开成功不能证明游戏连接成功。不要为方便而把整个 VM 防火墙关闭，也不要把公网反代当作 UDP 联机替代品。

## 修改与恢复

先保存 `.env`，再记录当前 `git rev-parse HEAD` 与镜像 ID。更新代码和构建完成后再替换容器。这个版本尚未设计持久化玩家账号、战绩数据库或网页管理权限，不要假设存在这些能力。

`.env` 改动用 `docker compose up -d --force-recreate`，仅 `restart` 不会重新读取 Compose 的环境变量配置。BSP、插件或源码改动需要重新构建。BOT 导航与学习数据目前在容器文件层，重新创建容器会恢复镜像内默认数据；不要把学习数据视为持久存档。

## 需要真实验证的内容

正式开放前至少在两台同事电脑上验证：一人进队后出现 BOT；第二人加入后 BOT 数量减少；一人退出后按目标补回；切换地图后 BOT 导航正常；战斗、声音、购买、中文快捷菜单正常；连续 30 分钟无断开或明显卡顿。

逐档测试 3、5、6、8 总角色，同时记录 `docker stats`、CPU 每核占用、实际内存和客户端延迟。CPU 单核长期接近满载、延迟波动或出现丢包时，先减少 BOT 数量/难度，再调整 CPU 资源。不要只凭服务器总体 CPU 百分比判断是否有余量。

## 自定义地图

`fy_iceworld` 不随此版本保证提供。加入自定义地图时要同时具备：合法取得的 BSP 和附属资源、匹配的 YaPB `.graph`、包含新资源的网页 ZIP 与新的版本清单。仅把 BSP 放进服务器目录会造成客户端缺资源，只有地图没有导航也不代表 BOT 能正常游玩。
